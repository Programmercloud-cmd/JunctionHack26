# Agentic chat branch

This branch starts at `origin/bugfix-linus` (`1f40e8d`) and now uses the user-requested Concrete project/session overview, which supersedes the earlier Home/Details navigation. The user's November 15 request supersedes the historical Decisions sufficiency preflight, reasoning-tier routing, rejection of Hydrogen for reconstruction, and bounded reconstruction-loop policy on the product chat path. Existing compatibility routes remain available.

`POST /api/chat` receives the exact original message, existing workspace/revision identity, optional `annotation_ids`, and optional document-free conversational history (`{role,content}`). One Gemini router chooses `conversation`, `technical_basic`, `technical_advanced`, `render`, or `ui`; it does not decide source sufficiency or rewrite the factual question. The response retains request/document/revision/navigation identities and adds `tool`, `message`, optional `answer`, optional `job`, and validated UI `actions`. Conversation works without an uploaded source. Technical workers need original drawing pages or native IFC records; their own answering call may clarify or return insufficient/unclear. No preflight gate runs. Factual support review and deterministic citation/calculation checks remain. `Answer.gate` is null on this path.

The conversation and technical workers may request the same basic-model UI capability. Its typed actions resolve against the captured saved catalog. The follow-up UI request restores source/IFC downloads, source attachment and explicitly supplied-value corrections. Corrections use existing typed input validation, exact revision/floor/object scope and edit authorization before one background refinement job is scheduled; the browser never resubmits a model-authored mutation. Numeric values/units must occur in the user's original message. The capability can interrupt an existing job but cannot recursively answer questions or implicitly generate geometry. Original pages remain factual authority; navigation catalogs, assistant history, generated geometry, annotations, and concept styling never become original-source facts. Direct UI controls stay inference-free.

The Linus Home/details layout now includes the released Active tasks panel and Concept tab. Source attachment accepts related multi-file drawings through the existing grouped-source store; genuine native IFC remains standalone. Downloads reuse saved originals/IFC without inference. A visible supplied-values panel reuses the attributed refinement workflow. Task snapshots include other saved buildings for authorized workspace members; anonymous public views receive no private task list. Rendering still follows its unchanged explicit interruption/consensus policy.

Control refreshes must not reinsert the chat column when it already has the correct parent. Moving a focused textarea loses focus, and reparenting its scroll container resets the reader's position. Chat updates follow the bottom only when the reader was already near it; background progress cannot force a reader away from older messages.

Explicit requests to use supplied measurements retain their typed values even when the message also says “in the blueprint” or describes what a drawing shows. Explicit source-only or ignore-input instructions retain precedence. Selected source measurements may add server-derived original-page pixel spans/reference scales, with user provenance and exact IDs, to worker/review context. These are reference calculations rather than printed scale facts or a uniform building calibration; source-only/native/model-space contexts exclude them.

Agent answer output allowances default to 8,192 tokens for the selected basic worker and 65,536 for the advanced worker. `GEMINI_AGENT_ANSWER_TOKENS` optionally overrides the selected worker and its corrective drafts. Advanced agent initial/corrective calls may use the remaining existing `QA_TOTAL_SECONDS` budget; basic and legacy draft ceilings stay unchanged. `GEMINI_AGENT_ANSWER_SECONDS` optionally overrides the agent call ceiling. Advanced QA uses model-default thinking unless `GEMINI_ADVANCED_THINKING_LEVEL` is explicitly set to a declared SDK level; basic QA stays low. Model choices, rendering/interpretation effort and the overall Q&A deadline remain unchanged. Output-limit and timeout responses are operational errors rather than evidence conclusions.

Model configuration is independent for basic conversation/QA, advanced QA, routing, UI, and rendering. Rendering defaults to `gemini-4-hydrogen` on three separate role-specific clients: one creator and two reviewers; there is no provider fallback or new dependency/framework. Existing legacy reconstruction configuration stays separate.

## Rendering

`POST /api/buildings/{id}/render` accepts `{base_revision_id,message,annotation_ids:[]}` and returns a persisted `render` job. Chat rendering and the visible Build model control use this route/tool. A separate executor leaves ordinary background question/extraction work available. The existing job polling and stop endpoints apply.

The latest user-selected call policy is one creator call followed by two review calls in parallel. The fixed creator proposes a description or typed patch using original sources and combined feedback from the previous round. The server generates/reopens IFC and applies local regression checks before submitting both reviews. Three separate provider clients keep creator and reviewer state apart; each reviewer receives a private snapshot of the exact same candidate and annotations, without the sibling's opinion. Both independently vote on a digest including description, reopened mesh/floor geometry, IFC bytes, and attributed values. Creator output alone is never an approval. Candidate changes clear previous votes. Typed patches preserve stable identities, source references, frozen frames, and user-provided provenance.

`parallel-hydrogen-v2` jobs record `call_policy:creator_then_two_parallel_reviews`. A valid full round makes three model calls; failed creation/local validation may return to the creator before reviews can run. Reviews use their own two-thread pool, keeping the existing background QA executor available. Partial votes appear as they finish, under stable reviewer numbers even when reviewer 2 finishes first. Publication waits for both results. A failed/stopped review pair drains in-flight requests before clients are reused or closed; existing per-request transport timeouts apply. Stop/source-change guards prevent late publication. No extra review or creator self-review call is introduced.

Creators receive compact incremental-patch guidance with a suggested outstanding focus, retaining all original sources, the complete description and all remaining review findings. Larger valid supported patches remain accepted. Output-limit retries request a smaller coherent correction; they preserve reviewed private progress and all unresolved findings. Safe per-call metadata is saved even on failed attempts and late completion after Stop, without reopening terminal jobs or recording provider bodies/private thoughts.

Only two satisfied, source-supporting votes for the same candidate complete the job. Both source-supporting votes may publish an intermediate preview while either reviewer still requests refinement. There is no maximum round count, total deadline, cost cap, repeated-proposal exit, or no-progress exit. Provider/schema/invalid-candidate failures remain visible, retain the previous usable revision, and retry after an interruptible delay. Existing per-request transport/output limits remain operational constraints, not a hidden successful stopping condition. Explicit Stop, shutdown/restart, or a concurrent source/revision replacement interrupts the job and prevents late publication. All three clients close when it exits. Satisfied reviewers do not certify building accuracy.

## Drawing and model marks

The later [projects and reversible marks contract](PROJECTS_AND_MARKS.md) adds Home project organization and revision-validated mark erasing/reactivation with session Undo/Redo. These operations keep original sources, model geometry and evidence authority unchanged.

`POST /api/buildings/{id}/annotations` saves `{revision_id,kind:point|stroke|measurement,space:source|model,points,label,value?,unit?,page?,source_id?,source_page?,object_id?,floor_id?}`. The server assigns `id`, building identity, timestamp, and `provenance:user_provided`. `GET` returns `{annotations:[...]}`. Marks are a filesystem sidecar; original source bytes and portable IFC source provenance are unchanged.

Source coordinates are original-page normalized XY. Model coordinates are mesh-local XYZ, pinned to an exact geometry revision and object identity per point (`point_object_ids`, matching the points array; `object_id` identifies the first point). Legacy single-object marks use that object for each point. A cross-object/storey stroke keeps each endpoint on its own object through orbit and floor separation. Marks from another revision are never silently rebound. Points have one anchor, strokes at least two, measurements exactly two distinct anchors plus an explicitly entered positive value/unit. No inferred screen/world distance is presented as a building measurement.

Selected mark IDs attach server-loaded marks to chat or rendering. Source-only factual QA cannot cite them as original evidence. A source measurement scoped to an explicit known floor can calibrate generation through the existing attributed input workflow; ambiguous floor scope asks the user to choose. Multiple consistent dimension marks share one floor calibration and every submitted mark/value remains attributed; conflicting scale inputs request a choice. Calibration remains user-provided, preserves original observations, and does not make assumed vertical geometry factual. Arbitrary model measurements identify a user request; they do not automatically reshape native IFC geometry.

For questions explicitly using attached dimensions, calculation operands reference either an inspected drawing evidence index or an exact permitted user-value ID. User operands require separate answer attribution and unchanged stored numbers/units. The server normalizes supported length units and validates/converts the output dimensions; computation records preserve the original attributed inputs separately. Source-only questions cannot use these inputs. Footprint means the exterior ground-floor outline, not one room or summed floor area. Conflicting plan calibration calls for clarification before extrapolating a whole-building estimate; it does not invalidate a direct calculation using the explicitly supplied dimensions of a region.
