# Projects and reversible user marks — 2026-11-15

Concrete Home lists projects with a first-page preview, editable name, Files icon/count, interpretation status and model availability. Clicking a project name, preview or Files icon opens its overview. The left column contains Files above saved Chats; the middle column is a rounded, explicitly read-only session preview; Active tasks stays on the right. With no selected preview, the middle panel displays the Concrete mark/name centered. The project list has no chat composer. The Home/Details tabs are removed; a home icon immediately left of the theme selector returns to the project list.

Opening a file reopens or creates a session for that file within the selected project. New chat creates a distinct project-owned session, choosing only that project's last-selected file, or no file for an empty project. Chat names resume live conversation; eye icons show previews with scrollable messages and expandable original-source evidence but no input fields. Chats have editable names, last-active date/time and red delete icons. Project names do not rename original source files. Original uploads, related-drawing grouping, explicit reconstruction, native IFC separation and drawing/model marks retain their existing semantics. The latest request supersedes the earlier project-to-last-file navigation.

Files can also be dropped directly onto a project row or anywhere on its Files page, with a visible drop area and target highlight. The target project is captured explicitly rather than changing the current project selection, and uploads reuse the normal validation/authentication/membership path. Busy uploads, read-only examples and locked workspaces reject drops. If a later file in a batch fails, earlier saved files are refreshed into the project list while the error remains visible. Project action buttons use theme surface/text colors so New project, Files and Rename remain legible in dark and light themes. Five focused browser tests passed after this follow-up, including real multipart multi-file drops to both targets, unchanged neighboring membership, invalid/busy/read-only rejection and at least 4.5:1 computed text contrast for the reported buttons in both themes.

Projects organize existing content-addressed saved bundles; they do not copy or merge source/model revisions. Identical uploads reuse the existing source/model and can be referenced from several projects. Removing a file from a project retains its saved source/model; Undo restores membership. Empty projects remain available. The first migration is recorded so removing the last project reference does not repeatedly recreate a project. Project names and the last-opened file survive restart. Original source bytes, building identities, revisions, question context and exports remain unchanged by project organization. Project-wide merged reasoning/model generation is not introduced.

Project metadata lives beside building bundles in `projects.json`. `GET /api/buildings` adds `projects`; create/rename use `POST /api/projects` and `PATCH /api/projects/{id}`. Membership uses `PUT|DELETE /api/projects/{id}/files/{building_id}`; resuming a file uses `PUT /api/projects/{id}/active-file/{building_id}`. Mutations require workspace authorization. Pinned public examples receive stable read-only project descriptors; anonymous catalogs contain no private project names/membership, and examples cannot be renamed or attached to editable projects.

Drawing tools now include Undo, Redo and a whole-mark Eraser in both source and saved-model views. Touching or dragging across strokes, points or measurement lines removes each complete touched mark. A single erase gesture is one reversible action, even when it crosses multiple marks. These edits affect user-authored sidecars only. Deleted marks are excluded from saved-mark choices and chat/render inputs; Undo restores their same stable IDs, coordinates, model-local object anchors, supplied values and attribution. Source pixels, model geometry and previously applied calibration are not edited by erasing a mark.

`PATCH /api/buildings/{id}/annotations` accepts `{revision_id,annotation_ids,active}`. The entire batch validates before saving; stale revisions and unknown IDs reject without partial edits. Soft deletion allows reactivation under the original revision and preserves provenance. Creating another mark retains deleted records needed by the current history. Existing GET and selected-annotation resolution return active marks only.

Undo/Redo cover creating and erasing marks within the current document/revision. A new drawing action clears Redo. Reload, switching files and replacement of source/model revision clear the browser history; persisted mark state remains saved. Page/view/camera changes within the same saved revisions retain history. Ctrl/Cmd+Z, Ctrl/Cmd+Shift+Z and Ctrl+Y work outside text fields; text inputs keep native text undo. Failed requests do not advance history. Buttons are disabled while a mark edit is pending or the saved example is read-only.

Navigate is now labeled **Pan / orbit**, with an explanatory tooltip/status: it turns drawing tools off, restores model camera controls and lets the source scroll normally. It does not move the camera to a destination or request inference. Clearing attachments continues to detach marks from the next message without erasing them.

## Project chat isolation and current verification

Product chat requires `project_id` and `session_id` at `/api/chat`. Before any model is created, the server verifies the project, session ownership, exact selected file and current project membership. An unscoped old page receives an actionable 422 instead of falling back to the last file. Empty-project sessions have no document/model/reference state. The server loads history from the session; client-supplied history never overrides it. Different sessions and projects remain separate even when they reference identical content-addressed originals. This is conversation/context isolation inside the existing shared workspace, not a new per-user account system. A chat inspects its selected file/source group; project-wide merged factual reasoning is not introduced.

Sessions persist under `project-chats/`. `GET|POST /api/projects/{project_id}/chats` lists/creates sessions; `GET|PATCH|DELETE .../chats/{session_id}` previews, renames or deletes one. Mutations and chat history require workspace access. Read-only public source/model browsing remains available without history or a composer; authenticated original-source QA still works on pinned examples. Session deletion hides/tombstones the session and prevents late appends or reimport. Source/model revisions and independent rendering jobs are unchanged.

Historical conversation records were file-scoped, so they import once as Previous conversation into the oldest existing project referencing that file. They are not copied into every project sharing the original. New product turns write only to their session. Historical building-level compatibility records remain retained; migration does not manufacture attribution for old requests that had no project identity.

The browser captures project/session identity and a session epoch alongside document/revision pins. File/session switching clears old history, annotations, focused objects, tour and camera references; metadata/history/answer responses cannot move the UI back to a previous project. Legacy background QA answers are not merged into new sessions. Read-only previews use their own DOM and never execute chat actions. Evidence controls only expand the captured original page inside that preview.

## Task navigation and microphone toggle

Chat rows now show only the editable name and last-active date/time; the filename description below the timestamp is removed. The composer microphone is a compact icon, muted by default. Click or keyboard activation toggles recording. Clicking again stops microphone tracks and finalizes an editable transcript without submitting it. Muting during connection startup stops a late stream; moving focus within the page keeps recording, while hiding the page mutes and changing sessions cancels it. Transcription readiness is separate from optional ElevenLabs spoken-answer readiness.

Active tasks and Recent activity are grouped by project. New jobs created from chat store immutable `origin` metadata with project, session, request and saved user-message IDs plus the original initiating message. Clicking a card opens that exact session, scrolls to and highlights the initiating message. Direct controls and uploads associate the captured project/session when available; historical and upload-only jobs without a recorded message open project Files. A deleted/unavailable chat also falls back to Files instead of resurrecting it. Nested source, Stop and task-detail controls retain their own actions.

Opening a terminal task dismisses its Recent activity entry after navigation succeeds. The rightmost red trash icon dismisses it without navigation. Both persist `activity_dismissed` on the saved job and retain job status, timestamps, events, original sources, results and chat history. Active work cannot be dismissed this way; clicking an active task navigates without stopping it. A later completion may appear as new Recent activity. These activity flags belong to the existing shared workspace, not per-user accounts.

The header arrow collapses the panel into a 36-pixel rail at the right screen edge; the opposite arrow expands it. The preference survives reload. Mobile starts collapsed unless a preference exists, expands as a right-side drawer, and collapses after selecting a task so its destination is visible. Project overview and live chat reuse the same panel.

`POST /api/jobs/{job_id}/origin` validates workspace edit access, project/file membership, session ownership and any claimed user-message/request pair before saving an immutable origin. `POST /api/jobs/{job_id}/dismiss` requires edit access and terminal job status. Neither endpoint changes inference, render-consensus or publication behavior.

Editable project rows have a red trash icon. `DELETE /api/projects/{id}` moves organization metadata into `deleted_projects` in the existing projects file, leaving shared originals, model revisions, jobs and session files saved. Tombstones survive restart and later create/rename/membership writes. This is project deletion, not permanent source-file erasure or automatic task cancellation.

Health adds `project_deletion_ready`; the browser hides project trash on an older API process lacking the endpoint. This supports updating static UI while an existing rendering process remains running. It is capability detection, not an additional authorization rule; the endpoints enforce access independently.
