## Small action/result contract

`POST /api/chat/actions` is an additive intent/validation route, not another job runner. Input: `message`, `request_id`, optional `document_id` and interpretation `revision_id`, plus a captured `workspace`. Output echoes request/document/revision identity and returns `status: ready|clarification`, `actions`, a brief non-factual `message`, and optional focused clarification/suggestions. Existing endpoints execute accepted operations; their results and errors update chat/workspace. The root-owned coordination proposal is authoritative for final operation names; the list below states required capabilities, not competing enum spellings. Root will freeze exact enums in `docs/CHAT_UI_CONTRACT.md` before dependent implementation.

Workspace explicitly stores document/building ID, interpretation revision, displayed geometry revision, view mode (`chat|source|model|concept`), selected IDs, focused ID, camera position/up/target, tour ordered IDs/index/running state, navigation highlighting, answer highlighting and assumption visibility. Also retain floor filter, separation, cutaway and source page/region where applicable. Document revision and geometry revision are distinct because a newer source interpretation can retain older usable geometry.

Use a strict discriminated action schema, with deterministic execution in declared order:

- `show_model` (reuse saved scene; existing reconstruction only when needed), `show_source`, `close_workspace`, `set_camera` (top/front/isometric/fit), `select` (validated IDs), `tour` (start/pause/resume/next/previous), `set_visibility` (answer highlights, navigation highlights, assumptions), `set_view` (inspection/concept), `set_floor`, `set_separation`, `set_cutaway`, `set_theme`.
- `question` forwards the original question and pinned context to the existing reviewed QA route; no factual answer is synthesized by the action interpreter.
- `refine` contains a validated existing `RefinementRequest` batch. Preserve exact user value, unit, scope, source support and attribution; route corrections through `interpretation_correction`. A bare request to improve the existing model uses existing reconstruction `mode: refine`.
- `list_saved`, `open_saved`, `attach_sources`, `new_upload`, `download_ifc`, `download_source`, `retry_extraction`, `stop_job`, `refresh`, `inspect_assumptions`, `inspect_inventory`, `set_comparison` cover existing application operations without separate settings/toolbars. File choice/download still uses browser-native controls reached through chat. Ambiguous saved building, floor, source, job or refinement scope requests a focused choice.

Gemini (or the explicitly configured OpenAI adapter) interprets language once using existing structured transport through an additive adapter. The prompt requests intent and reference selectors, never authoritative facts or fabricated IDs. Supply saved semantic labels/IDs/kinds/floors and current workspace context; no screenshot rediscovery or raw source image pass is needed for navigation. Code resolves `focused`, `selection`, named IDs/labels, kinds and floors against the correct saved revision, validating membership, renderability and source evidence. Duplicate labels produce clarification. Do not resolve by list index, nearest region or similarity guessed by the model. Unresolved objects remain available for source inspection and are excluded from mesh selection/tours.

An explicit modeled-window selection means all renderable, reliably associated saved window records in the requested scope, never every window in the real building or drawing. Report renderable/unresolved coverage without claiming extraction completeness. Native IFC source navigation uses the existing pinned record inspector; do not invent blueprint pages. Drawings use the original stored page/region exactly, including existing coarse-region limitations.

When no scene exists, `show_model` may carry a typed deferred selector such as `{kind:"window",floor_id:null}`. This is a pending navigation request, not a resolved identity list or an assertion that windows were reconstructed. Validate selector type and any existing floor scope immediately; once the existing job publishes an accepted usable scene, application code resolves it against that scene and validates renderability. A failed/stopped/no-mesh reconstruction stops dependent selection, camera and tour actions and reports the retained source/model state. Never manufacture IDs in anticipation of generation. A preview can be shown as preview while review continues, but the pending action must state that status rather than call it complete/reviewed.

Execute action batches in order. Each step returns completed, pending or failed; a pending operation suspends its dependent steps, and failure cancels those steps. Already completed harmless navigation is retained and described; do not claim transaction rollback. Validate the full persistent edit batch before submission using the existing atomic workflow. Do not combine unrelated persistent mutations into an implicit transaction. Output chat text is generated from validated action results/labels; the interpreter's prose cannot become an unreviewed factual answer. Clarification may use concise interpreter text but must ask about the genuine unresolved target/scope.

Malformed actions, absent targets, unsupported edits and stale persistent revisions fail before execution. A provider failure is a recoverable operational error, never source insufficiency or silent regex/fixture fallback. Compact chat buttons may emit typed deterministic actions without another model call. Keep existing upload/page/provider limits; one small intent call adds routing latency, not a second factual review.

## State and sequencing invariants

1. On every submit, synchronously pause the tour and capture an immutable snapshot before any await or queued timer can change focused ID. Cancel queued tour movement. Resolve “this window” against that snapshot. Preserve the captured source revision and stored evidence separately from current display state.
2. Apply asynchronous results only to their request/document epoch. A newer scene swap revalidates selection and tour IDs; removed/unresolved targets are explained and never replaced by another object. Stale refinements return 409 and request an explicit resubmission against the refreshed revision. Old source evidence can still open its pinned revision.
3. Keep navigation selection/highlighting separate from answer highlights and assumption display. Source navigation pauses the tour but preserves its IDs/index, camera and model revision. “Back to the model; next window” restores that tour and advances exactly once. Reaching the end reports completion rather than silently cycling.
4. Camera top-down preserves selection. Frame selection from actual world bounds with active floor offsets; close-ups use reliable geometry/host orientation where available. An ambiguous orientation uses a useful oblique fallback labeled as approximate; never claim an inferred exterior side or physical dimension. Manual orbit/pan/zoom continue to work and update captured camera state.
5. Reuse the existing prepared/atomic revision swap. Preserve surviving IDs, camera, modes and independent toggles. Rejected refinement leaves the previous usable scene visible. Pending, preview/unreviewed, reviewed-with-remaining-issues, stopped and failed states remain distinct in chat.
6. Preserve reliability-session `recovery_events`, `submitted_values`, and each event's base-revision source links when integration brings those additions in. Do not drop those fields while reformatting job cards.
7. Navigation, source inspection and compact actions remain usable while factual QA or reconstruction runs. Use per-request state rather than a global busy lock. Serialize persistent mutations through existing job rules; reject stale results without erasing the next message draft or a newer user navigation. Maintain an explicit navigation epoch, incremented by submit, compact navigation or deliberate gesture start, separately from document epoch and interpretation/geometry revisions. Orbit damping/render ticks do not increment it. A response may mutate the workspace only if its captured epoch still owns the pending navigation; otherwise retain its result in chat without moving the view. A pending reconstruction continuation is tied to its request/epoch and cannot override later navigation. Old source links remain usable through their captured revision even after a stale action is discarded.
8. Keep ephemeral navigation/upload/progress turns in a keyed client message ledger and merge persisted server QA turns by request/job/message IDs. `refreshConversation` must not replace the entire ledger and erase navigation or duplicate answers. Restoring ephemeral navigation turns across a full browser restart is not required; persisted building QA remains the existing authoritative history, and the UI must not claim navigation history was saved.

## Bounded implementation sequence

1. Establish the contract and deterministic interaction fixtures before polishing layout. Fixtures inject provider/action responses and are explicitly labeled test data; no production mock switch or fixture answer fallback.
2. Implement additive routing and validation against existing snapshots. Unit-check malformed/unknown references, duplicate-label ambiguity, stale document/geometry contexts, scoped refinement payloads, native IFC source behavior and provider errors.
3. Implement viewer selection framing, top-down and focused-object close-ups using existing meshes/controls. Add explicit snapshots and pauseable tour state. No source/IFC/geometry mutation.
4. Build Chronicle chat presentation and migrate existing upload, polling, answer/citation, operation and failure presentation into chat. Provide keyboard-accessible attachment/action/citation controls, live progress announcements and retained message drafts.
5. Integrate accepted action execution with existing endpoints. Upload shows “Reading your drawings…” until validated interpretation is available; say sources are retained on failure. QA works before 3D. Requested 3D reuses a cached scene or displays existing job progress. Retain pending semantic selection until newly generated geometry is available, then resolve against that actual revision.
6. Run fixtures, actual artifact/backend checks and live-provider checks separately, then independent implementation/browser review. Fix blockers through bounded re-review, record remaining limitations and make focused local commits only.
