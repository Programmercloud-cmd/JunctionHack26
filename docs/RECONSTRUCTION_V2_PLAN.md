# Drawing description → deterministic IFC → viewer

Independently reviewed plan; implementation contract is RECONSTRUCTION_V2_CONTRACT.md. This user-requested extension supersedes the single-floor/no-openings restriction. Keep the current local app, original-source sufficiency gate, providers, and Three.js viewer. Gemini describes visible building information; Python validates and deterministically constructs IFC using IfcOpenShell. Never execute model-generated Python or accept model-generated IFC.

## Deliverable and exclusions

Process the unchanged original image or all available uploaded PDF pages. Identify separately depicted floor diagrams, their visible labels, room footprints, boundary segments and clearly visible door/window openings. Generate only depicted floors. Reuse a cached generated IFC and its tessellated scene across questions. No manual pre-cropping/rotation requirement. Retain normalized coordinates on the original page, even when a floor diagram needs a local transform for display.

Implement rooms, storeys, simple boundaries and demo-quality openings. Defer stairs, roofs, inferred unseen floors, structural/MEP completeness, new formats, remote rendering and photorealism. Unknown relationships produce an explicitly schematic/exploded arrangement, not an invented aligned building.

## Shared extraction contract (root finalizes models)

`BuildingDescription {version, floors[], limitations[]}`. Each floor has a server-assigned stable ID, visible label or neutral display label, `source {page, bbox}`, `rooms[]`, `boundaries[]`, `openings[]`, and optional supported ordering/orientation/measurement observations. The model returns local references; server validates and assigns persistent IDs.

- Every room: label, original-page polygon, source region. Every boundary: original-page segment/polyline and source region. Every opening: door/window, original-page endpoints or region, host-boundary reference if reliably identified, source region. A room or opening label is a fallible image interpretation, never independently authoritative.
- Measurement observations retain printed text, interpreted value/unit when readable, the measured feature/reference, original-page evidence and explicit known/unknown state. Do not fabricate a scale from standard door sizes or similar buildings. Recording a dimension does not prove a uniform page scale or common scale between floor diagrams.
- Floor identity/order/orientation/alignment each need original evidence or explicit unknown. Repeated/ambiguous diagrams on multiple pages are not automatically additional storeys. Unresolvable duplicates remain separate source diagrams with warnings; do not assert their building relationship.
- All geometry validation runs before IFC construction. Preserve valid partial results with omission warnings; reject no-survivor results. Conflicting polygons are evaluated within the same floor only. Current all-pairs overlap handling remains; do not repair malformed polygons, choose arbitrary overlap winners or drop rooms silently.
- A floor may acquire a supported scale only from a clear source reference segment and its stated physical length/unit. Server validates endpoints and computes the conversion deterministically; the model cannot assert a free-standing metres-per-pixel value. Keep `scale_status=known|unknown` per floor and retain calibration evidence. Unknown floors remain relative; a mixed building has no global metric claim. Original images/pages stay in the provider answering path.

One bounded extraction request describes the uploaded drawing pages, with source page labels. Keep current operational failure behavior and MAX_TOKENS rejection; never accept truncation as completeness. Do not introduce arbitrary new floor/room caps. Existing upload/resource limits remain explicit. The former single-floor 30-room extraction limit cannot silently become a whole-building cutoff: root must explicitly resolve/remove that restriction and communicate any changed limit before implementation. Generated models must obey existing IFC byte/element/triangle safeguards with clear errors, not truncated inventories.

## Unknown scale: explicit IFC semantics

For unknown or mixed scale, use an `IfcContextDependentUnit` for LENGTHUNIT named `UNSCALED_DISPLAY_UNIT`, with length dimensional exponent 1. This is not an `IfcSIUnit` claiming metres. Source-derived coordinates use a documented per-floor frame; the frame transform and original page region are persisted. Floors with unknown relative scales are not comparable by model distance. A supported calibration can produce metric coordinates for an individual known-scale floor, with its conversion/evidence recorded separately; it does not promote the mixed artifact to metres. Only if every depicted floor has supported calibration may root choose an SI-metre project/scene, still distinguishing inferred geometry from measured source observations.

Feasibility checked locally against installed IfcOpenShell: replacing a sample IFC's length unit with this context-dependent unit preserved its name through STEP serialization/reopen and tessellated a wall successfully. `calculate_unit_scale()` returned 1, so that utility alone is insufficient to identify metres. The generated-artifact importer must detect this unit/provenance and emit `Scene.units="relative"`; its tessellation numeric convention is not a physical measurement. Implementer must add a fresh generated-file roundtrip test, not rely only on the sample experiment.

Assumed extrusion heights, boundary thicknesses, opening heights and window sill heights are display assumptions in relative units, stored separately from source observations. Unknown storey elevations remain unknown. Storeys may share a local elevation for storage; viewer-only exploded offsets expose them without suggesting measured vertical spacing. Preserve each diagram's orientation unless a supported transformation exists; unknown inter-floor alignment remains schematic. Show this distinction before the first model and in the inspector/export metadata.

## Deterministic IFC and provenance roundtrip

Proposed pure boundary: `generate_ifc(description, document_id, source_manifest) -> bytes`, plus a validated artifact manifest decoded by root's importer integration. The final signature follows root's shared model. IFC4 hierarchy: project → building → storeys, rooms as IfcSpace, boundaries as IfcWall, visible doors/windows as IfcDoor/IfcWindow. Generate deterministic GlobalIds from document/artifact namespace plus stable element IDs; never use random IDs on every question/reopen.

For reliably hosted openings, generate IfcOpeningElement with void/fill relations and deterministic simple geometry. Opening horizontal extent comes from interpreted source pixels; missing vertical extents use clearly recorded display assumptions. If a host is ambiguous, omit that opening's generated geometry and report it; do not cut an arbitrary wall or invent a door. No extraction retry loop or geometry-repair model call. Boundary deduplication/host mapping must preserve source references and cannot erase a legitimate separate floor boundary.

Persist a versioned project artifact manifest and per-element provenance in the IFC itself, using dedicated property sets. It includes: generated-from-drawings marker; scale status; source page identity/digests/dimensions; floor IDs/labels/transforms/calibrations; GlobalId→original page/region mapping; assumptions; omissions; and all visual-layout decisions. Embed the original normalized source-page PNG bytes as base64 project properties, keyed by page identity/digest. These are the actual source previews, not rendered models, model-created images or reduced evidence summaries. This makes the downloaded IFC self-contained for source QA after standalone reopening. The manifest/source images must be read independently of the native importer's first-48-property inspector/first-12-property QA views. No hidden sidecar or same-process registry dependency.

Root must distinguish **native source IFC** from **drawing-derived IFC** before native catalog/source-context creation. Generated geometry remains `geometry_origin="inferred"`, `source_kind="image"`, `catalog_complete=false`, original image SourceRefs, honest scale status and visible warnings after tessellation/reopen. IFC GlobalIds remain scene element IDs; original source IDs/regions survive as provenance. Do not route generated IFC through native IFC factual count/property shortcuts. Mark generated facts/assumptions as derived, never source properties. Invalid/incomplete generation manifests fail closed as derived artifacts, rather than silently becoming authoritative native IFC.

Downloading and reopening a generated IFC preserves inferred status and restores embedded original pages for QA. Validate base64, hashes, PNG decode/pixel limits, manifest page identity and all source coordinate bounds before use. Existing 25 MiB IFC import/export and decoded-image safeguards apply; embedded base64 can exceed this limit even when the original compressed upload was smaller, so report that explicit export limitation instead of truncating pages or introducing hidden new limits. If originals are absent, malformed or inconsistent, reject the generated artifact rather than treating its model as source evidence. Genuine uploaded IFC behavior remains unchanged; provenance flags are an evidence policy, not proof of authenticity of arbitrary third-party files.

Valid rooms/walls/openings may highlight only when their actual source reference supports the answer; otherwise keep source evidence without a highlight. Do not add a deterministic generated-scene count path.
