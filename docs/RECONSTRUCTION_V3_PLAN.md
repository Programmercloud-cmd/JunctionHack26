Independently reviewed plan; review resolutions are in RECONSTRUCTION_V3_CONTRACT.md. Concrete shared fields are owned by root in `docs/RECONSTRUCTION_V3_CONTRACT.md`; that contract governs implementation. Preserve the existing original-drawing → Gemini description → deterministic IfcOpenShell → generated IFC → Three.js pipeline, portable source provenance, source-based QA, caching and stable selections. The user's new scope includes every meaningful depicted building/furnishing feature as reconstructed geometry, a labeled schematic, or an explicit unresolved source item. ## Diagnosis grounded in the saved final artifacts

Inspected the unchanged original `colorful-11397.png`, `/tmp/junction-live-v2-final/colorful-11397.png.ifc`, its matching scene JSON and the saved viewer image. The final IFC and scene agree: two storeys, 11 spaces, 57 walls, one door, no windows, and no stairs/furnishing elements. Every scene element has a mesh. Two terrace/balcony spaces are represented as ordinary rooms with ten automatically generated perimeter walls. These are actual IFC modeling/description limitations, not missing viewer meshes.

The current generator turns every retained room polygon edge into a wall. Room polygons describe usable spaces, not a structural wall inventory: this invents enclosure on outdoor edges, can duplicate shared boundaries and can turn a mistaken door-leaf/arc-shaped room boundary into a wall. In the inspected final artifact the diagonal wall centerlines are on the exterior-space outlines; we have not established that this exact run traced a door leaf. The design nevertheless permits that failure and must stop deriving walls from room perimeters.

The schema cannot represent indoor/outdoor distinctions, independent boundaries, stairs, tables, cabinets or sanitary objects. The current prompt requests only selected openings, and opening hosts depend on retained room-edge indices; invalid/omitted room polygons can therefore remove otherwise visible openings. Some failed openings are summarized only as a count. The result cannot account for meaningful unrendered features individually.

The separate `/tmp/medium-quality-description.json` is another run: two floor records, 12 room records and four opening records. It is useful evidence of extraction coverage, but cannot explain individual omissions or geometry in the final IFC above. The saved final `1794` artifact has six spaces, 30 walls, five doors and two windows; use it as a regression baseline, not a ground-truth inventory.

## Narrow description changes (root finalizes contract)

Keep named x/y and left/top/right/bottom on the wire, original-page coordinates internally, existing floor regions/transforms/calibration/alignment/measurements, and medium reconstruction reasoning unless controlled live evidence warrants another choice. Extend each floor with the following compact records; no new arbitrary list caps.

- `rooms`: retain label/polygon/basis/note; add `environment: indoor|outdoor|unknown`. These produce footprint plates only. Unknown classification remains visible; it does not authorize enclosure. A terrace/balcony footprint is allowed without known elevation, floor thickness or railing height.
- `boundaries`: local stable `key`, `kind: wall|railing|open_edge`, label, original-page segment, source region, `thickness_segment` (empty if unknown), basis and concise note. One record per physical segment, shared by neighbouring spaces. Trace the depicted wall/railing itself; never door leaves, swing arcs, furniture edges or inferred room rectangles. Keep width/extrusion as current explicit display assumptions unless a valid thickness segment supplies depicted width. An open edge is recorded as open; it must not produce a wall.
- `openings`: retain door/window kind, label, original segment, source region and basis/note; replace `host_room/host_edge` with `host_wall: boundary key|null`. The host must be the correct same-floor explicit wall. Missing/ambiguous hosting is unresolved, not a guessed nearest wall. Unknown height/sill is compatible with a schematic opening and an explicit display assumption.
- `features`: `kind: stairs|table|chair|cabinet|bed|sofa|sink|toilet|shower|bath|appliance|other`, label, source region, polygon, basis and note. Source polygons may be approximate footprint symbols; unresolved geometry belongs in the unresolved list. Do not discard a visible object solely because its vertical dimensions are unknown. Stairs may be a low schematic footprint/tread indication; do not infer an actual rise, direction or connection between floors. Distinguish object geometry from the walls that surround it.
- `unresolved`: label, category, original source region and reason for visible but unclassifiable features or uncertain geometry. Server validation failures must produce equivalent persistent outcomes, not disappear into a warning count. Avoid duplicating the same item in feature and unresolved input lists. Group inseparable repeated symbols explicitly when individual source extents cannot be resolved.

Keep extraction to the existing bounded request. Ask the model to account for the meaningful depicted categories across each entire floor, including openings and furnishings, without restricting it to a few illustrative examples. Model omissions are not automatically detectable: the inventory is a reconstruction audit aid, not a certified complete list or factual count source. Meaningful feature coverage needs a source-by-source visual acceptance pass.

## Deterministic generator behavior

1. Validate spaces, boundaries, openings and features independently. Invalid room polygons must not suppress valid explicit walls or openings. Existing room conflict rules remain within each floor; do not repair polygons or infer missing structural partitions.
2. Emit footprint plates for indoor/outdoor spaces with distinct provenance/classification and viewer styling. Emit IfcWall only from explicit wall records; emit railing geometry only from explicit railing records. Open edges remain visibly open. Shared boundary IDs map to one wall. Exact repeated/reversed copies can be recognized and reported; conflicting or uncertain duplicate interpretations remain unresolved rather than arbitrarily choosing one or silently merging nearby geometry. Duplicate/conflicting local boundary keys must never resolve by array order: mark the conflicting records and dependent openings unresolved unless identity is unambiguous.
3. Attach door/window void/fill relations only to their validated wall ID. Validate original endpoints/source bbox/floor consistency and the existing host-wall-band projection. Keep actual boolean openings in the IFC, rather than painting symbols on solid walls. If hosting fails, retain that exact opening as an unresolved inventory/source item. No automatic migration to a neighbouring wall and no widening source regions to force acceptance.
4. Generate simple, visibly differentiated feature geometry. Tables/cabinets may use IfcFurnishingElement, sanitary features an appropriate supported IFC product or generic furnishing subtype, and stairs a schematic product/footprint rather than a fabricated inter-storey connector. A small set of deterministic primitives is enough; this is not an asset library or detailed furniture modeling project. Record all display heights, thicknesses and other absent dimensions as assumptions.
5. Give every extracted/validated item a persistent compressed IFC GlobalId in its floor namespace. Persist its category, source, resolution status and reason. Unresolved entries become geometry-less semantic IFC entities with matching scene records; they have no invented mesh or location beyond their valid original source region. If malformed coordinates prevent reliable localization, use the known floor region explicitly marked coarse/unlocalized; do not manufacture a precise bounding box. Stable IDs survive validation omissions, caching and download/reopen. These inventories remain explicitly derived, never authoritative building counts.

Replace “at least one room must survive” with the reviewed contract's “at least one supported renderable element”: usable explicit walls/features may survive room interpretation failure. All-unresolved results remain explicit no-3D failures; do not claim a model was built. Root should retain the extraction/unresolved diagnostic payload for inspection when possible. This changes a current invariant and must be communicated; it is not a new feature-count limit.

Kinds extend to room/outdoor/wall/railing/open_edge/door/window/stairs/furniture/fixture/other. This avoids forcing furniture into the old taxonomy or maintaining a redundant separate inventory. Keep unknown/partial coverage explicit. Reader checks stable IDs, actual IFC classes/storeys, source associations and all new status/semantic fields against per-element Psets. Unresolved entities are deliberately geometry-less entries in the generated catalog, not native source facts.

Add source geometry needed for meaningful comparison to manifest provenance where useful, but never use the provider's description as proof that rendered IFC matches it. All source images and per-floor transforms continue to survive download/reopen. Generated inventories, feature classes and dimensions are association hints only; the original-source QA gate and actual-height refusal remain unchanged. Extend validated highlight types only with appropriate source evidence; unresolved items open source evidence without fabricated mesh selections.

Retain the scene/download endpoints and cached model behavior. Root adds computed `Scene.comparison: PlanComparison[]`, with element_id/floor_id/page/layer, original-coordinate polygons/lines, method and optional cut_height. Compute after tessellation and recompute on reopening; never trust stale persisted comparison paths. Do not add an extra inference call or rebuild IFC for each overlay/selection. Source-overlay visibility remains separate from answer highlighting and assumptions controls.

## Source overlay must compare the actual IFC

Root's `app/comparison.py` computes the comparison from tessellated generated IFC meshes (and actual hosted void/fill geometry when needed), transformed back through the inverse stored floor matrix to the original page. The frontend places those vectors on the unchanged source image with separate layers for boundaries, indoor/outdoor footprints, openings, schematic features and unresolved regions. The overlay must not simply redraw the model's intended polygons or bounding boxes and call that a geometry check.

A full-height wall footprint projection hides opening cuts because the lintel above an opening projects over the gap. Either use appropriate mesh cross-sections or explicitly overlay actual IFC opening/fill footprints alongside projected wall footprints, with a clear legend. Do not claim that an uncut projection proves opening correctness. Compare multiple original floor regions on the same image without applying viewer explosion or display rotation to the source. Native source clicks, floor filtering and restored embedded pages must continue to work.

The UI should make unresolved items inspectable individually: selecting one shows its original region and reason. Show concise category/status totals for navigation, labeled as reconstruction inventory, not building facts. The user can inspect broad coverage without reading a long warning paragraph or searching only a selected set of doors.

## Design constraints to explain before implementation

- Independent explicit wall extraction replaces a wrong inference, but adds description content. The current token budget may then be exhausted; token-limit/provider failures remain operational errors. Run both live originals early. If a split extraction or budget change becomes necessary, root must explain that new call/budget tradeoff before implementing it; do not silently truncate furnishings/openings or add sample-count caps.
- Missing physical heights do not block schematic reconstruction. Assumptions remain visible and cannot answer factual height questions. Unknown scale, orientation, registration and inter-floor elevations retain current semantics.
- Source/host/geometry checks can leave clearly visible features unresolved. They must remain in the portable inventory and overlay, with reasons. This may still block visual acceptance if major recognizable features are absent; a successful HTTP status alone is not success.
- Existing upload, IFC byte/element/triangle and response safeguards remain. Additional source-linked features increase artifact size; oversized artifacts fail explicitly rather than silently dropping features/pages.
- Schematic feature silhouettes are sufficient for this hackathon. No new file formats, hidden-floor inference, structural completeness, parametric CAD editing, photorealism, cloud rendering or extra agent runtime.
